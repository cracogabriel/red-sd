# RED: mflix Movie Manager

A distributed movie management system built with Python and Java as part of the Distributed Systems course.  
The server exposes CRUD operations over a TCP socket using Protocol Buffers. The client is a Java Swing GUI that communicates with the server.

## Problem Statement

Proposed by Prof. Rodrigo Campiolo as part of the Distributed Systems course. The goal is to implement a remote service for managing movies from the MongoDB Atlas **sample_mflix** dataset. The server receives requests via TCP, processes them against the database, and returns serialized responses. All communication uses **Protocol Buffers** as the binary serialization format.

## Supported Operations

| Operation     | Description                                               |
| ------------- | --------------------------------------------------------- |
| Create        | Inserts a new movie into the database                     |
| Get           | Fetches a single movie by ID                              |
| Update        | Updates an existing movie by ID                           |
| Delete        | Removes a movie by ID                                     |
| List by Actor | Returns movies featuring a given actor (case-insensitive) |
| List by Genre | Returns movies from a given genre (case-insensitive)      |

## Protocol

All messages between client and server are serialized using **Protocol Buffers** (proto3).  
The schema is defined in `movie.proto` and shared between both sides.  
Each side generates its own language-specific classes from the same `.proto` file using `protoc`.

The server keeps the TCP connection open and handles multiple sequential requests per client. The client opens a new connection for each operation.

---

## Proto Design

The schema defines a `Movie` message with all relevant fields (title, year, genres, cast, directors, etc.), and three lightweight request-only messages used to carry operation-specific parameters: `MovieIdRequest` (an ID string for GET and DELETE), `ActorRequest`, and `GenreRequest`.

The key design decision is a **single `Request` message** that encapsulates all six operations:

```proto
message Request {
  Operation operation = 1;  // enum: CREATE, GET, UPDATE, DELETE, LIST_BY_ACTOR, LIST_BY_GENRE

  Movie          movie     = 2;  // used by CREATE and UPDATE
  MovieIdRequest by_id     = 3;  // used by GET and DELETE
  ActorRequest   by_actor  = 4;  // used by LIST_BY_ACTOR
  GenreRequest   by_genre  = 5;  // used by LIST_BY_GENRE
}
```

Only the field relevant to the chosen operation is populated, the others are left empty. This means the client and server share a single message type for all requests, and the server switches behavior based on the `operation` field alone, without needing to define a separate message type per operation.

The same idea applies to the response side with a **single `Response` message**:

```proto
message Response {
  bool   success = 1;
  string error   = 2;

  Movie          movie   = 3;  // GET, CREATE, UPDATE
  repeated Movie movies  = 4;  // LIST_BY_ACTOR, LIST_BY_GENRE
  string         message = 5;  // DELETE
}
```

A failed response always has `success = false` and a descriptive `error` string. A successful response populates only the field that matches the operation: a single movie, a list of movies, or a plain message string for DELETE. This keeps the protocol simple: one request type in, one response type out, regardless of the operation.
